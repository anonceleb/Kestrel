This is FIDE's D-1 acceptance test — nothing here is softened

Five admitted gaps, closed. What's still open, stated with the same prominence.

A threat-model review named these five holes explicitly. Closing them was a precondition of this demo shipping, not a nice-to-have — a contribution whose own threat model contradicts its neutrality claim doesn't get a meeting.

Closed

1. Registry write authorization

CLOSED

Was: Registry.register()/suspend() and Vault.erase() had no caller-identity check at all — anyone holding a reference could admit, suspend, or erase any participant or subject. Now: both require a signed WriteAuth credential from an already-registered, active role: "facilitator" participant, verified the same way every inter-participant request is.

tests/grant-core/gap-fixes.test.ts — INV-29, INV-29b

2. Self-signed default disclosure policy

CLOSED

Was: defaultPolicyStore() generated a throwaway keypair, signed the policy with it, and discarded the key — Platform could "sign" its own policy changes with a key nobody else ever held. Now: demoOnlyInsecurePolicyStore() throws DemoPolicyNotAllowed unless CFP_ALLOW_DEMO_POLICY=1 is explicitly set, and warns loudly even then. Every real construction path must supply an operator-signed PolicyStore.

tests/grant-core/gap-fixes.test.ts — INV-30, INV-30b

3. Adapter log-hygiene coverage

CLOSED

Was: tools/privacy-lint's log-hygiene scan walked only packages/ and services/ — skipping the one directory whose code is most likely to legitimately touch plaintext. Now: the scan also walks adapters/ and profiles/. Proven non-vacuous the same way the original lint gate was: injecting a PII-shaped console.log into a scratch adapter directory makes the lint exit 1.

tests/grant-core/gap-fixes.test.ts — INV-31

4. Root-secret placement

CLOSED

Was: Platform.issueS2ID(root, merchantId) was a method on the Zone-2 class, taking a RootSecret as a plain argument — nothing stopped it from being wired to a network endpoint reachable from a consumer's wallet. Now: pairwise-ID issuance exists only as Vault.issuePairwiseId, in Zone 1. There is no method anywhere on Platform's public surface that accepts a RootSecret — checked structurally, not by discipline.

tests/grant-core/gap-fixes.test.ts — INV-32

5. Platform-side cross-merchant correlation

CLOSED

Was: ConsentEntry.subject was a stable root-identity reference, visible to Platform across every consent entry regardless of counterparty — Platform itself could correlate a subject by comparing subject values, the exact correlation pairwise IDs exist to prevent for merchants. Now: subject is a pairwise reference, derived per-counterparty. Two entries for the same real subject under different counterparties share no comparable value.

tests/grant-core/gap-fixes.test.ts — INV-33

§3.1 — Beckn alignment constraints (added after founder review — binding)

Three requirements added to the build prompt after this demo first shipped. All three are now addressed; the middle one honestly, not by pretending a live integration exists.

3.1.1 Registry as a Beckn network-registry client

CLOSED

Was: a self-minted Ed25519 registry — its own participantId, its own trust anchor, no relationship to Beckn's actual subscriber convention. Now: identity is subscriberId (FQDN-shaped, per Beckn's subscriber_id convention), envelopes carry Beckn's real wire format — keyId="{subscriberId}|{keyId}|ed25519", digest is a BLAKE2b-512 hash of the canonical body ("BLAKE-512"), signing string is the exact (created)/(expires)/digest: shape published at developers.becknprotocol.io. Registry's docstring now frames it explicitly as simulating a real Beckn network registry's subscribe/lookup wire protocol in-process — a real deployment swaps the in-memory map for HTTP calls with zero change to envelope generation/verification.

tests/grant-core/beckn-envelope.test.ts — INV-34

3.1.2 DeDi (dedi.global) directory integration

CLOSED — AS INTERFACE

Was: no DeDi interface anywhere. Now: packages/directory/src/directory.ts defines DeDiDirectoryPort — publish/lookup for operator label-signing keys, capability/subscriber revocations, and signed disclosure-policy entries — wired so it's actually exercised: OperatorKeyring.rotate(), Registry.suspend(), NonceLedger.revoke(), and PolicyStore.reload() all publish through it. Stated plainly, here and in the file's own header comment: InProcessDirectory is an in-memory demo backend, not a live dedi.global integration. DeDi requires network/chain calls, which conflicts with this repo's "runs entirely offline" property — the interface is the honest shape of what a real integration would implement; nothing here talks to dedi.global's actual REST API.

tests/grant-core/directory-port.test.ts — INV-35

3.1.3 No-discovery boundary stated explicitly

SATISFIED

Was already true — no search/catalog/matching code exists anywhere in this repo — but the README didn't say so in as many words. Now it does: see the "Scope: where CFP begins" section — CFP begins after discovery; every flow starts from an already-formed order/grant context.

Still open — pilot scope

Offline double-redemption

verifyLabelOffline() checks signature, expiry, and key validity window only — it cannot know whether the underlying grant was already burned online. Two couriers scanning the same still-valid artifact before either syncs would both see a valid artifact; only the first to actually call Vault.resolve() succeeds, but the artifact itself doesn't reveal this offline. Not solved here.

Carrier-identity binding

No binding exists between a grant and the specific carrier/relay identity redeeming it. An mTLS-bound carrier identity is the spec's own named answer to the gap above — not attempted in this codebase.

Depot-time resolution as a synchronous dependency

Resolution is a once-per-parcel online event. In a deep-rural network the "depot" can be a low-connectivity branch office, not an urban sortation hub — an unresolved empirical question about whether the address-driven savings survive that reality, not a solved one. See spec/CFP-v0.x.md §9.

The stewardship commitment

D-1, stated verbatim — the FIDE acceptance test for this page

A time-box whose clock the steward controls is not a time-box. Transfer to a named neutral home — FIDE/NFH or ONDC's extension governance — no later than twelve (12) months after CFP v0.1 publication, whether or not a working group has formed by then. This clause is operative regardless of working-group status; "no group has formed yet" is not a condition that extends the twelve months.

The grant-core invariant suite (tests/grant-core/) is donated under open license (Apache-2.0, this repository) today — forkable now, not conditional on the clause above triggering. The clause governs who holds the pen after twelve months, not whether the suite is open before then. Same text, same commitment, in spec/CFP-v0.x.md §8.
