What closed, what's open, and who holds the pen

A threat-model review named five holes explicitly; closing them was a precondition of this demo shipping. Each closure below names the test that pins it — run npm run verify. Open problems follow, stated with the same prominence.

Closed

1. Registry write authorization — closed

Was: Registry.register()/suspend() and Vault.erase() had no caller-identity check — anyone holding a reference could admit, suspend, or erase. Now: both require a signed WriteAuth from an already-registered, active facilitator, verified the same way every inter-participant request is. gap-fixes.test.ts · INV-29, INV-29b

2. Self-signed default disclosure policy — closed

Was: defaultPolicyStore() signed the policy with a throwaway key nobody else held. Now: demoOnlyInsecurePolicyStore() throws unless CFP_ALLOW_DEMO_POLICY=1 is explicitly set, and warns even then; every real construction path must supply an operator-signed PolicyStore. gap-fixes.test.ts · INV-30, INV-30b

3. Adapter log-hygiene coverage — closed

Was: the privacy-lint log-hygiene scan skipped adapters/ and profiles/ — the code most likely to legitimately touch plaintext. Now it walks both; proven non-vacuous by injecting a PII-shaped console.log into a scratch adapter and watching the lint exit 1. gap-fixes.test.ts · INV-31

4. Root-secret placement — closed

Was: pairwise-ID issuance was a Zone-2 Platform method taking a RootSecret argument — nothing stopped it being wired to a network endpoint. Now it exists only as Vault.issuePairwiseId in Zone 1; no method on Platform's public surface accepts a RootSecret — checked structurally, not by discipline. gap-fixes.test.ts · INV-32

5. Platform-side cross-merchant correlation — closed

Was: ConsentEntry.subject was a stable root-identity reference — Platform itself could correlate a subject across counterparties, the exact join pairwise IDs exist to prevent for merchants. Now subject is a per-counterparty pairwise reference; two entries for the same real subject under different counterparties share no comparable value. gap-fixes.test.ts · INV-33

Beckn alignment constraints (added after founder review — binding)

3.1.1 Registry as a Beckn network-registry client — closed

Was: a self-minted registry with its own trust anchor. Now: identity is FQDN-shaped subscriberId, envelopes carry Beckn's wire format — keyId="{subscriberId}|{keyId}|ed25519", BLAKE2b-512 canonical-body digest, the exact (created)/(expires)/digest: signing string published at developers.becknprotocol.io. Registry simulates a real network registry's subscribe/lookup surface in-process; a live deployment swaps the in-memory map for HTTP with zero change to envelope code. beckn-envelope.test.ts · INV-34

3.1.2 DeDi (dedi.global) directory integration — closed as interface

packages/directory defines DeDiDirectoryPort — publish/lookup for operator label-signing keys, capability/subscriber revocations, and signed policy entries — and it is actually exercised: OperatorKeyring.rotate(), Registry.suspend(), NonceLedger.revoke(), and PolicyStore.reload() all publish through it. Stated plainly, here and in the file header: InProcessDirectory is an in-memory demo backend, not a live dedi.global integration — DeDi needs network/chain calls, which conflicts with the runs-entirely-offline property. The interface is the honest shape of what a real integration implements. directory-port.test.ts · INV-35

3.1.3 No-discovery boundary — satisfied

Already true — no search/catalog/matching code exists in the repo — and now stated in as many words: README § "Scope: where CFP begins". CFP begins after discovery; every flow starts from an already-formed order/grant context.

Still open — pilot scope

Offline double-redemption — open

verifyLabelOffline() checks signature, expiry, and key validity window only — it cannot know whether the grant was already burned online. Two couriers scanning the same still-valid artifact before either syncs both see a valid artifact; only the first Vault.resolve() succeeds, but the artifact itself doesn't reveal that offline. Not solved here.

Carrier-identity binding — open

No binding exists between a grant and the specific carrier/relay identity redeeming it. An mTLS-bound carrier identity is the spec's named answer to the gap above — not attempted in this codebase.

Depot-time resolution as a synchronous dependency — open

Resolution is a once-per-parcel online event. In a deep-rural network the "depot" can be a low-connectivity branch office — whether the address-driven savings survive that reality is an unresolved empirical question (D-2), not a solved one. See spec §9. If outage-driven failures eat the savings, the design moves to asynchronous pre-resolution.

The stewardship commitment (D-1, verbatim)

A time-box whose clock the steward controls is not a time-box. Transfer to a named neutral home — FIDE/NFH or ONDC's extension governance — no later than twelve (12) months after CFP v0.1 publication, whether or not a working group has formed by then. This clause is operative regardless of working-group status; "no group has formed yet" is not a condition that extends the twelve months.

The grant-core invariant suite (tests/grant-core/) is donated under Apache-2.0 today — forkable now, not conditional on the clause triggering. The clause governs who holds the pen after twelve months, not whether the suite is open before then. Same text in spec/CFP-v0.x.md §8.
