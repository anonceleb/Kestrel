What closed, what's open, and who holds the pen

A threat-model review named five holes explicitly; closing them was a precondition of this demo shipping. Each closure below names the test that pins it — run npm run verify. Open problems follow, stated with the same prominence.

Two items below are tagged with short reference codes, D-1 and D-2, used consistently in this project's internal review notes and carried here so a reader can cite the same point across this page and spec/CFP-v0.x.md: D-1 is the stewardship-transfer clause (§8), D-2 is the depot-time / rural-precision open question (§9).

Closed

1. Registry write authorization — closed

Was: Registry.register()/suspend() and Vault.erase() had no caller-identity check — anyone holding a reference could admit, suspend, or erase. Now: both require a signed WriteAuth from an already-registered, active facilitator, verified the same way every inter-participant request is. gap-fixes.test.ts · INV-29, INV-29b

2. Self-signed default disclosure policy — closed

Was: defaultPolicyStore() signed the policy with a throwaway key nobody else held. Now: demoOnlyInsecurePolicyStore() throws unless CFP_ALLOW_DEMO_POLICY=1 is explicitly set, and warns even then; every real construction path must supply an operator-signed PolicyStore. gap-fixes.test.ts · INV-30, INV-30b

3. Adapter log-hygiene coverage — closed

Was: the privacy-lint log-hygiene scan skipped adapters/ and profiles/ — the code most likely to legitimately touch plaintext. Now it walks both; proven non-vacuous by injecting a PII-shaped console.log into a scratch adapter and watching the lint exit 1. gap-fixes.test.ts · INV-31

4. Root-secret placement — closed

Was: pairwise-ID issuance was a Zone-2 Platform method taking a RootSecret argument — nothing stopped it being wired to a network endpoint. Now it exists only as Vault.issuePairwiseId in Zone 1; no method on Platform's public surface accepts a RootSecret — checked structurally, not by discipline. gap-fixes.test.ts · INV-32

5. Platform-side cross-merchant correlation — closed by construction in the ledger, by convention at the call site

Was: ConsentEntry.subject was a stable root-identity reference — Platform itself could correlate a subject across counterparties, the exact join pairwise IDs exist to prevent for merchants. Now subject is a per-counterparty pairwise reference in the ledger; two entries for the same real subject under different counterparties share no comparable value there. The caveat: createGrant currently accepts whatever subjectRef string the caller passes — it is pairwise "by convention in this codebase," not a type the ledger enforces. The convention already gets bent inside this repository's own tests (literal "rider_1", "sub_1"). A nominal PairwiseRef type, checked at createGrant, closes this by construction — planned, not yet built. gap-fixes.test.ts · INV-33

Beckn alignment constraints (binding design decisions)

3.1.1 Registry as a Beckn-convention signing layer over a stub registry — envelope format closed; trust anchor and role vocabulary still self-minted

What changed: identity is FQDN-shaped subscriberId, envelopes carry Beckn's wire format — keyId="{subscriberId}|{keyId}|ed25519", BLAKE2b-512 canonical-body digest, the exact (created)/(expires)/digest: signing string published at developers.becknprotocol.io. Registry simulates a real network registry's subscribe/lookup surface in-process; a live deployment swaps the in-memory map for HTTP with zero change to envelope code. What did not change: the envelope format is Beckn-shaped, but the trust root is not — Registry is still an in-process Map with its own genesis facilitator as trust anchor, not a client of any real Beckn network registry. All five ParticipantRole values (merchant, operator, brand, platform, facilitator) are locally invented and occupy the slot where Beckn's subscriber_type (BAP/BPP/BG) belongs; tier is a locally-defined accreditation ordinal, not a Beckn concept. Call this "a Beckn-convention signing layer over a stub registry," not "a Beckn network-registry client." beckn-envelope.test.ts · INV-34

3.1.2 DeDi (dedi.global) directory integration — wired and tested half-step, not a drop-in

packages/directory defines DeDiDirectoryPort — publish/lookup for operator label-signing keys, capability/subscriber revocations, and signed policy entries — and it is actually exercised: OperatorKeyring.rotate(), Registry.suspend(), NonceLedger.revoke(), and PolicyStore.reload() all publish through it. Stated plainly, here and in the file header: InProcessDirectory is an in-memory demo backend, not a live dedi.global integration — DeDi needs network/chain calls, which conflicts with the runs-entirely-offline property. What swapping in the real thing costs: every port method today is synchronous and returns void; a network-backed implementation makes every call site above async — a refactor through the middle of the codebase, not a new adapter class behind unchanged signatures. Entries also carry no publisher proof, no record version, and no namespace, all three of which DeDi's real create/read surface needs. Call this days of work, not hours — an invitation to build it together against a real namespace, not a claim that it's already nearly free. directory-port.test.ts · INV-35

3.1.3 No-discovery boundary — satisfied

Already true — no search/catalog/matching code exists in the repo — and now stated in as many words: README § "Scope: where CFP begins". CFP begins after discovery; every flow starts from an already-formed order/grant context.

Still open — pilot scope

Offline double-redemption — open

verifyLabelOffline() checks signature, expiry, and key validity window only — it cannot know whether the grant was already burned online. Two couriers scanning the same still-valid artifact before either syncs both see a valid artifact; only the first Vault.resolve() succeeds, but the artifact itself doesn't reveal that offline. Not solved here.

Carrier-identity binding — open

No binding exists between a grant and the specific carrier/relay identity redeeming it. An mTLS-bound carrier identity is the spec's named answer to the gap above — not attempted in this codebase.

Depot-time resolution as a synchronous dependency — open

Resolution is a once-per-parcel online event. In a deep-rural network the "depot" can be a low-connectivity branch office — whether the address-driven savings survive that reality is an unresolved empirical question (D-2), not a solved one. See spec §9. If outage-driven failures eat the savings, the design moves to asynchronous pre-resolution.

Threshold-split vault keys — open

The vault's key-management (Kms) is single-custodian — no m-of-n split. Named as an open question in spec §9, not attempted in this codebase.

The DIGIPIN precision floor is a constant, not a k-anonymity rule — open

The address adapter truncates DIGIPIN to a fixed 6 characters (a ~0.90 km² cell) with no justification tied to population density anywhere in this codebase. The core does enforce a real, tested K_ANON_FLOOR = 25 — but it is wired to brand-cohort visibility, never to geography. Against the repository's own asserted k≥50, a 6-character cell fails below roughly 55 people/km²; against the core's enforced k=25, it fails below roughly 28 people/km². Both thresholds sit above large parts of rural India. The fix is an adaptive rung — shortest DIGIPIN prefix meeting a k-anonymity floor over bound subjects, not a constant — not yet built.

Gap #5's convention is not yet a construction — open

See item 5 above: Platform.createGrant accepts any string as subjectRef today. The ledger enforces pairwise separation once a value is stored, but nothing stops a caller from passing a non-pairwise identifier in the first place. A nominal PairwiseRef type returned only by derivePairwiseId, checked at createGrant, is the planned fix.

The stewardship commitment (D-1, verbatim)

A time-box whose clock the steward controls is not a time-box. Transfer to a named neutral home — FIDE/NFH or ONDC's extension governance — no later than twelve (12) months after CFP v0.1 publication, whether or not a working group has formed by then. This clause is operative regardless of working-group status; "no group has formed yet" is not a condition that extends the twelve months.

The grant-core invariant suite (tests/grant-core/) is donated under Apache-2.0 today — forkable now, not conditional on the clause triggering. The clause governs who holds the pen after twelve months, not whether the suite is open before then. Same text in spec/CFP-v0.x.md §8.
